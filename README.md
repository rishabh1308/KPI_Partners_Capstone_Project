# KPI Partners Capstone Project -- MegaMart Supermarket Chain Data Engineering

A Python- and SQLite-based data engineering project for centralizing and
analyzing sales, inventory, supplier, and purchase-order data for
MegaMart, a fictional supermarket chain operating five stores in
Hyderabad, India.

The project demonstrates a small end-to-end data pipeline: raw CSV
generation, data validation and cleaning, relational database loading,
SQL-based business analysis, inventory replenishment analysis, supplier
performance analysis, and an interactive Streamlit dashboard.

## Project Overview

MegaMart needs a centralized way to manage and analyze information
generated by its stores. The project uses CSV files as the source data,
Python for validation and ETL, SQLite for structured storage, SQL for
business analysis, and Streamlit with Plotly for visualization.

The pipeline is designed to keep accepted records separate from rejected
records and to preserve a log of validation decisions.

### Stores covered

-   HITEC City
-   Banjara Hills
-   Ameerpet
-   Kukatpally
-   Dilsukhnagar

### Main data domains

-   Stores
-   Products
-   Suppliers
-   Sales transactions
-   Inventory
-   Purchase orders

------------------------------------------------------------------------

## Business Problem

The supermarket chain's operational data is spread across separate
files. Data-quality problems such as duplicate transactions, missing
optional information, invalid product prices, inconsistent phone
formats, and invalid references can reduce the reliability of business
reporting.

MegaMart needs a process that can:

1.  Validate and clean incoming CSV files.
2.  Store clean data in a normalized relational database.
3.  Enforce data integrity through primary keys, foreign keys, and check
    constraints.
4.  Analyze sales by product, store, month, and category.
5.  Identify low-stock products and estimate replenishment quantities.
6.  Evaluate supplier delivery performance.
7.  Present the results in an interactive dashboard.

## Database Design

The SQLite database is named `megamart.db`.

### Tables

  ---------------------------------------------------------------------
  Table                              Purpose
  ---------------------------------- ----------------------------------
  `stores`                           Store details and manager
                                     information

  `suppliers`                        Supplier details and contact
                                     information

  `products`                         Product names, categories, prices,
                                     and supplier references

  `sales_transactions`               Individual sales records

  `inventory`                        Product stock held by each store

  `purchase_orders`                  Orders placed with suppliers
  ---------------------------------------------------------------------

### Relationships

-   A supplier can supply multiple products.
-   A store can have multiple sales transactions.
-   A product can appear in multiple sales transactions.
-   A store can hold multiple products in inventory.
-   Each inventory row refers to one store and one product.
-   A supplier can receive multiple purchase orders.

### Integrity rules

The schema uses:

-   Primary keys to uniquely identify records.
-   Foreign keys to maintain valid relationships.
-   `CHECK` constraints to reject invalid values.
-   A uniqueness constraint on `(store_id, product_id)` in the inventory
    table.
-   A check that a sales transaction's `total_amount` equals
    `quantity_sold * unit_price`.
-   A check that a purchase order's delivery date is not earlier than
    its order date, when a delivery date is present.

SQLite foreign-key enforcement must be enabled on each database
connection using:

``` python
connection.execute("PRAGMA foreign_keys = ON")
```

## Data Pipeline

The pipeline follows these stages:

``` text
Raw CSV Files
     |
     v
CSV Inspection
     |
     v
Data Validation and Cleaning
     |
     +--------------------+
     |                    |
     v                    v
Processed CSVs       Rejected CSVs
     |
     v
SQLite Database
     |
     v
SQL Analysis
     |
     v
Streamlit Dashboard
```

### 1. Generate sample data

The sample data generator creates six CSV files in `data/raw/`.

Run:

``` bash
python scripts/generate_sample_data.py
```

The generated data includes intentional quality issues for validation
practice.

### 2. Inspect source CSV files

Run:

``` bash
python scripts/check_csv_files.py
```

The inspection step checks the available files, columns, and record
counts.

The supplied generator produced the following raw record counts during
this project:

  File                         Records
  -------------------------- ---------
  `stores.csv`                       5
  `products.csv`                    14
  `suppliers.csv`                    5
  `sales_transactions.csv`       2,004
  `inventory.csv`                   70
  `purchase_orders.csv`            300

The sales file contains 2,000 original transactions plus four
deliberately injected duplicate records. Although the generator's
message may say five duplicates, the actual loop condition creates four
for the configured 2,000 records.

### 3. Create the database

Run:

``` bash
python scripts/create_database.py
```

This executes the schema script and creates the SQLite database.

### 4. Validate and clean the data

Run:

``` bash
python scripts/data_validation.py
```

The validation pipeline reads raw CSVs, applies data-quality rules, and
writes accepted and rejected records to their respective directories.
Validation messages are written to `outputs/data_validation.log`.

### 5. Review rejected records

Run:

``` bash
python scripts/analyze_rejections.py
```

This helps summarize why records were rejected.

### 6. Load validated data

Run:

``` bash
python scripts/data_loader.py
```

The loader inserts validated data into SQLite. It enables foreign-key
enforcement, uses a transaction, deletes existing rows in
child-to-parent order before reloading, and inserts parent records
before dependent records.

### 7. Verify the database

Run:

``` bash
python scripts/verify_database.py
```

The verification script checks table counts, foreign-key integrity,
sales amount calculations, and inventory uniqueness.

### 8. Run analytical scripts

``` bash
python scripts/sales_analysis.py
python scripts/inventory_analysis.py
python scripts/purchase_analysis.py
```

These scripts contain the SQL-based business analysis.

## Data Quality Rules

The validation pipeline addresses the following issues.

  ---------------------------------------------------------------------
  Data issue                         Validation / treatment
  ---------------------------------- ----------------------------------
  Missing store manager              Allowed as `NULL`; warning logged

  Missing supplier contact person    Allowed as `NULL`; warning logged

  Invalid product price              Rejected when price is zero or
                                     negative

  Inconsistent supplier phone format Normalized where possible

  Known injected duplicate sales     Rejected

  Ambiguous sales with matching      Preserved for review rather than
  business attributes                automatically deleted

  Invalid foreign-key reference      Rejected

  Missing purchase-order delivery    Allowed as `NULL`; treated as
  date                               pending

  Invalid inventory quantity         Rejected if it violates the
                                     inventory rules

  Sales or inventory referring to    Rejected because the product
  rejected products                  reference is invalid
  ---------------------------------------------------------------------

### Duplicate handling

The project distinguishes between known synthetic duplicates and
ambiguous matching records.

The generator's known duplicate convention creates a duplicate
transaction ID 10,000 greater than the original ID. This convention is
used only to identify deliberately injected duplicates in this sample
dataset. It should not be treated as a general duplicate-detection
strategy for production systems.

Records with matching business attributes but without this known
generator pattern are preserved for review because two legitimate
purchases can share the same attributes.

## How to Run the Project

Run the pipeline in this order when building the database from raw data:

``` bash
python scripts/generate_sample_data.py
python scripts/check_csv_files.py
python scripts/create_database.py
python scripts/data_validation.py
```

Then run the analytical scripts:

``` bash
python scripts/sales_analysis.py
python scripts/inventory_analysis.py
python scripts/purchase_analysis.py
```

Finally, launch the dashboard from the project root:

``` bash
python -m streamlit run dashboard.py
```

Streamlit will print a local URL in the terminal, usually:

``` text
http://localhost:8501
```

Open that URL in a browser.

> Run the commands from the project root so that the relative directory
> structure remains consistent. The Python scripts use paths derived
> from their own file locations where implemented.

### Inventory analysis

A fixed low-stock threshold of 20 units identifies four store-product
combinations:

-   Coca Cola 1.5L at Kukatpally: 0 units.
-   Coca Cola 1.5L at Dilsukhnagar: 0 units.
-   Shampoo 200ml at Ameerpet: 3 units.
-   Shampoo 200ml at Banjara Hills: 14 units.

The demand-based replenishment analysis uses historical sales to
estimate stock coverage. Its assumptions are:

-   Average daily demand = annual units sold / 366, because 2024 was a
    leap year.
-   Reorder trigger = fewer than 14 days of stock coverage.
-   Target stock = 30 days of demand.
-   Suggested reorder quantity = maximum of zero and the ceiling of (30
    days of demand minus current stock).

The recorded demand-based recommendations were:

  Store          Product            Current stock   Suggested reorder
  -------------- ---------------- --------------- -------------------
  Dilsukhnagar   Coca Cola 1.5L                 0                  17
  Ameerpet       Shampoo 200ml                  3                  13
  Kukatpally     Coca Cola 1.5L                 0                  10

The fixed threshold and demand-based policy answer different questions.
For example, Banjara Hills Shampoo is classified as low stock under the
fixed 20-unit threshold but has approximately 47 days of stock coverage,
so it does not meet the 14-day demand-based reorder trigger.

## Assumptions and Limitations

-   The project uses generated sample data; the findings should not be
    interpreted as actual business performance.
-   The low-stock threshold of 20 units is an exercise assumption.
-   The demand model uses 2024 sales as a proxy for future demand. It
    does not model seasonality, promotions, lead-time variability, or
    safety stock.
-   The demand calculation uses 366 days for the 2024 leap year.
-   The suggested reorder quantity targets 30 days of demand and does
    not include incoming purchase orders.
-   The current `purchase_orders` table does not contain product-level
    order items or ordered quantities. Therefore, the dashboard cannot
    calculate inventory on hand plus stock on order.
-   The inventory valuation analysis multiplies stock quantity by
    product listed selling price. It is an estimated selling-price
    value, not accounting inventory cost.
-   A NULL delivery date is treated as a pending order. It does not
    necessarily mean that the order is late.
-   Supplier completion rate measures recorded deliveries, not on-time
    delivery performance.
-   The generator-specific duplicate ID pattern is only suitable for
    this synthetic dataset.
-   The current interactive store explorer filters its own store-level
    section; it is not a global filter applied to every dashboard
    visualization.
